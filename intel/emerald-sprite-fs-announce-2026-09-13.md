## 1. 先講好量具，再講量到什麼（否則讀數沒有意義）

**路徑**：`preview_start {url: …/prototype/?demo=1}` 開瀏覽器分頁（不需要 dev server）→ 清 SW 與 caches →
`HL.games.launch(HL.games.byId("emerald-sprite"))`＝**玩家點卡片走的那一條**（不是 CLAUDE.md §9 那個繞過 `mountView` 的 headless 配方）。

**量具**：`MutationObserver` 掛在 `.ax-sprite__stage` 子樹上，記 `data-beat` 變動（**帶 `attributeOldValue`**）、
彈分節點的加入、以及盤面每一次重畫時的 `(還在轉的格數 / 中獎格數 / ⭐ 數)`。時間用 `performance.now()`。

**正向對照（誠實條款第 6 條）**：同一把尺量 `shadow-ritual`（既有款、同品類）——
6 轉分別記到 **9／9／7／2／6／2** 次分階段變動、跨 5.7／5.9／3.9／1.2／3.9／1.2 秒。
⇒ 量具會動、而且分得出「贏的轉比輸的轉長」。**若沒有這一組，下面每個讀數都可能只是儀器壞掉。**
⚠️ 據實：`shadow-ritual` **完全沒有 `data-beat`**（它早於這個慣例），所以對照組只在「分階段變動」這個通道上成立，
`data-beat` 那個通道**沒有對照組**——下面關於 beat 的結論，靠的是 `oldValue` 這個獨立證據，不是對照。

## 2. 10a／11a 的正面讀數（結構層 → PASS）

一轉（無連鎖的輸局）的實測時間軸：

```
t=2    beat=reveal      30 格全在轉
t=120  25 格在轉   ← 第 1 欄落定
t=231  20 格        ← 第 2 欄
t=356  15 格        ← 第 3 欄
t=481  10 格        ← 第 4 欄
t=607   5 格        ← 第 5 欄
t=731   0 格        ← 第 6 欄落定
t=855  beat=settle
```

**逐欄由左而右落定、每欄約 120–125 ms**＝slot 的期待階段真的存在（非瞬間平板結算）⇒ **10a PASS**。

連鎖局（`reveal → clusterwin → drop → clusterwin → drop → settle`）與分級回饋實測：

| 觀測 | 讀數 |
|---|---|
| 中獎拍→落下拍的停留 | 6 格團 437 ms、大團更久（`300 + min(團大小,16)×22` 的實現） |
| 彈分分級 | 小獎無 class、`is-big`（實測 `🎉 39.62×`）、`is-mega`（≥100×）、金格另有 `is-gold` |
| 輸局 vs 連鎖局 | 873 ms vs 2,207–5,487 ms |

⇒ **11a PASS**（回饋確實隨贏額/團大小分級，不是 2× 與 500× 同一種）。
⚠️ **10b／11b（好不好看、舒不舒服）仍為 `UNVERIFIED`**——這條路量得到拍序與拍距，量不到補間動畫。

## 3. 缺陷一：**retrigger 在它自己落地之前就被說出口**

強制種子 167（node 先算好：觸發免費遊戲、**第 4 轉自帶 +5 retrigger**），線上實測那一轉：

```
t=3691  彈分「🔄 +5 免費轉數！」      ← 公告
t=3691  HUD「免費遊戲 4 / 15」        ← 計畫轉數已經從 10 改成 15
t=3691  盤面：30 格全在轉、⭐ 數 = 0   ← 這一轉才剛開始轉
t=3816  ⭐ 數 = 2
t=4064  ⭐ 數 = 3                     ← 第 3 顆 ⭐ 到這裡才落地（晚 373 ms）
t=4424  0 格在轉                      ← 整排到這裡才停（晚 733 ms）
```

**玩家在那一轉開始旋轉的同一毫秒，就已經知道自己 retrigger 了。**
那一轉接下來的 733 ms——也就是這款遊戲**唯一真正的高潮時刻**——全部沒有懸念。

根因是一行的位置：公告與 HUD 上修寫在 `revealSpin()` **之前**。
數學完全正確（`sp.retrig` 就是那一轉自己掙來的），錯的是**說出口的時機**。
對照保真閘：第 9 項逐字要求「RNG 先於動畫（**client 不可偷看**）」，第 10 項要求期待感存在於品類的關鍵張力點。

## 4. 缺陷二：**`fsstart` 這一拍從來沒有存活過一幀**

同一次量測，免費遊戲進場的瞬間出現兩筆 `data-beat` 記錄、**時戳完全相同**：

```
t=860  {from: "reveal",  to: "reveal"}
t=860  {from: "fsstart", to: "reveal"}
```

第二筆的 `oldValue` 證明屬性**確實被寫成過 `fsstart`**；而兩筆落在同一個 microtask、
callback 讀到的現值都已經是 `reveal` ⇒ **`data-beat="fsstart"` 沒有活過任何一幀**。

意義不只是「我的量具看不到」：
- 任何 `[data-beat=fsstart]` 的 CSS（未來要做免費遊戲進場動畫的自然寫法）**永遠不會套用**；
- 任何下游觀測者同樣看不到；
- CLAUDE.md §10.1 第 5 條的紀律逐字是「**節奏類改動：每一拍都寫進 `data-beat` ⇒ headless 也能驗出拍的順序**」——
  一個零寬的拍，等於讓那條紀律對這一段**失效而不報錯**。

而在玩家眼裡：免費遊戲的進場公告與第一轉的旋轉**同時發生**，沒有一個屬於它自己的瞬間。

## 5. 修法：把「拍序」從一串 DOM 呼叫變成**可驗的資料**

缺陷住在演出層，而演出層當時**沒有任何可被 node 檢查的東西**——它就是一串直接操作 DOM 的呼叫。
所以修法不是移動那一行，而是先給它一個可以被斷言的形狀：

| 新出口（`HL.emeraldSprite`） | 是什麼 |
|---|---|
| `fsPlan(spins, fast, pace)` | **純函式**：把整段免費遊戲攤成有序的拍（`announce` / `hud` / `reveal` / `steps` / `tail`），每拍帶 `ms` |
| `playFsPlan(plan, ops)` | **依賴注入的播放器**：照順序把每一拍交給 `ops`，帶 `ms` 的拍在效果之後才 `delay` |

兩條不變量現在寫在 `fsPlan` 裡，而不是散在 view：
1. **公告不得早於見證它的那一次落定**——`hud` 拍在 `reveal` 之前、且顯示的計畫轉數是 `planned − retrig`；
   `announce(retrig)` 拍排在該轉 `reveal` **之後**，這時才把轉數改成 `planned`、才彈「+5」。
2. **結構拍要有寬度**——進場 `fast ? 60 : max(420, 900×pace)`、retrigger `fast ? 40 : max(260, 620×pace)`。
   下限是刻意的：長 bonus 會把 `pace` 壓到 0.25，**壓縮演出可以，壓掉結構拍不行**（同 `HL.battleTempo` 的既有結論）。

`playFsPlan` 刻意寫成「**效果同步就同步往下走、遇到 thenable 才轉非同步**」：
瀏覽器裡 `reveal`/`steps`/`delay` 都回 promise ⇒ 行為與一般 promise 鏈完全相同；
而本專案的自我檢測是同步的，這樣 node 才能用記錄用 `ops` **把整條拍序真的跑一遍**再斷言順序——
不是讀原始碼猜順序（§4 形狀⑦「認寫法」）。

## 6. 鎖：`games/emerald-sprite/fs-announce-after-witness`

**為什麼既有的 `cascade-beat-structure` 沒守住**：它守的是**基礎局**的連鎖時間軸（`steps` 的 land/win/drop）
與逐欄落定排程。它沒有錯，它的**射程沒有到免費遊戲的演出層**——而那正是兩條缺陷住的地方。
（這與 09-13 平台軌那條「煙霧偵測器對自己點的火沒反應」是同一族：鎖沒壞，是**它認的那一組訊號不包含新東西**。）

新鎖的斷言（全部在 node、無 DOM）：

- **(a) 見證者**：種子 167 必須真的跑出「觸發免費遊戲 + 某一轉自帶 retrigger」。失去見證者就**明文轉紅**並要求換種子，不是靜靜放行。
- **(b)** 用記錄用 `ops` 跑完整條拍序，效果數必須夠多（否則後面的順序斷言是空的）。
- **(c)** `announce(retrig)` 的序位必須 **> 該轉 `reveal`** 的序位。
- **(d)** 該轉落定前的 HUD 計畫轉數 == `planned − retrig`；公告拍 == `planned`、`add == retrig`。
- **(e)** 沒有 retrigger 的轉**不得**出現 retrigger 公告（擋「乾脆每轉都彈」這種假修法）。
- **(f)** 第一個效果是 `announce(enter, beat=fsstart)`、**緊接一個 `ms>0` 的停留**、且第一次 `reveal` 排在其後。
- **(g)** 極速模式兩個結構拍仍 `ms>0`、一般模式比極速久、`pace=0.25` 時仍守得住 400／250 ms 下限。
- **(h)** 唯一一條「認寫法」的斷言，只認一件事：**view 真的把這份排程播出去**
  （`playFsPlan(fsPlan(` 逐字、**先剝註解與字串字面量**、且必須落在會被求值的語法位置）。
  沒有它，(a)–(g) 全對而畫面可以完全不照它走。

**負向擾動 14/14 CAUGHT**（逐條見 loop-journal）。其中三條特別值得記：
- 把公告搬回 `reveal` 之前（＝還原成本輪修掉的那個缺陷）→ (c) 轉紅；
- 把呼叫塞進 `void 0 && …` 與「只留字串字面量、實際呼叫改名」→ (h) 兩種繞法都轉紅（§4 形狀⑦(b)(e)）；
- 拿掉 `Math.max` 下限 → 一般讀數全對、**只有 `pace=0.25` 那條轉紅**（結構拍下限的存在理由）。

## 7. 給後手的三句話

1. **「數學對」與「說出口的時機對」是兩件事。** RTP 蒙地卡羅、賠付常數、拓樸鎖——本款全部都有，
   而它照樣在 733 ms 的高潮裡把答案先講了。**演出層需要它自己的不變量**，不能靠數學閘順便守。
2. **零寬的拍等於沒有那一拍。** 只要 `beat(x)` 與下一個 `beat(y)` 之間沒有 `await`，`data-beat` 就不會以 `x` 存活；
   寫了 `beat()` 不代表那一拍存在。要驗，就用 `attributeOldValue`。
3. **這兩條都只在「線上站 × 真實路徑」看得見。** node 測項全綠、源碼鎖全綠、畫面看起來完全正常。
   09-12 那一輪的發現（排程輪可以用 `preview_start {url}` 對線上站跑玩家路徑）在這一輪第一次真的抓到東西——
   而且抓到的是**上一輪自己剛寫的程式**。
